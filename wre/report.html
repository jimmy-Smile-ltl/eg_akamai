01Object

被测对象

wre 是一个 Rust 工具链，在主包本地起一个 sidecar 可执行文件 wred，在 V8 realm 里执行厂商自己的 sensor 脚本，并使用录制的 Mac 设备、行为与传输指纹。Python 客户端通过 JSON-RPC 驱动它。

仓库proofofbots/web-re-toolkit · MIT · Rust
包 / 运行时wre-client-akamai 3.1.1 / wre-runtime 3.1.1
sidecarwred.exe · 61,314,560 bytes（win_amd64）
覆盖classic V2/V3 sensor ✓ · pixel ✓ · PoW 已实现但未验证 · interstitial ✗
官方验证站login.xero.com、matrix.leeclerk.org（Lee County search）

注意覆盖边界：interstitial / bm-verify 只做解析、不做求解；文档写明研究集里没有站点下发过这一类挑战，因此官方也没有 live 样本。

02Method

方法：先证伪，再求解

每一站都先证明“裸请求会被拒”，再交给 wre；否则 200 可能本来就 200，无法归因。全程串行、低频，只取公开首页。

STEP 1curl 裸测Chrome UA、无 cookie；403 或 000 才说明存在传输层保护。
STEP 2discoverprotected=True 且 sensor=obfuscated 才算候选。
STEP 3solve产出 _abck、posts、telemetry，记录耗时。
STEP 4request同 session 再 GET，比较 status 与内容长度。
判定条件
validated_abck field[1] == 0 且 validated=True
unvalidated仍为 -1，但同 session 页面 200
incrementcurl 403（或 000）→ wre 复查 200
failedsolve 报错 / 超时 / 被 403
03Install

安装：一次镜像，61MB 二进制

py -3.12 -m venv venv
venv\Scripts\python.exe -m pip install wre-client-akamai \
  -i https://pypi.tuna.tsinghua.edu.cn/simple --timeout 120

直连 PyPI 在 files.pythonhosted.org 反复 ReadTimeout；换清华镜像后 22.8MB wheel 以 10.9MB/s 一次装好。wheel 解压带出 61MB 的 wred.exe（V8 静态链接），首次运行不额外下载，启动 0.3–3.7s。

专题固定在 eg_akamai/wre/；60MB+ 的 venv 与 wred.exe 不随仓库发布，脚本与台账只作为测试记录。

06Experiments

三个对照实验

6.1通过不靠 cookie，靠 TLS / HTTP-2 指纹

把 wre 会话里的完整 Cookie 头（2,192 字符，含 _abck、bm_sz、HCSESSIONID、visitorid）原样交给普通 curl：

$ curl 无 cookie → 403 $ curl + wre cookie (2,192c) → 403 $ wre 同 session → 200 · 482,454 bytes

结论：cookie 不是通过原因；wreq-util 的传输指纹才是。这也解释了 _abck 仍为 -1 时页面照样 200。

6.2_abck 不稳定，页面更稳

站点validated页面 200
www.ibm.com3/33/3
www.tokopedia.com3/33/3
www.britishcouncil.org2/33/3
login.xero.com2/22/2
www.akamai.com1/22/2
www.apahotel.com0/44/4

同站、同参数复跑，_abck 会随机落回 -1；页面 200 反而更稳定。验证状态与可访问性不是一回事。

6.3PoW 分支从未触发

所有站的 _abck field[4] 都是 -1，PoW 难度从未下发。与官方“PoW 已实现但未在真实站验证”的描述一致。

08Boundary

与 gatekit 的边界：互补，不重叠

这次实测的结论不是“换掉 gatekit”，而是分工。

维度gatekit（eg_akamai）wre
靶子interstitial bm-verify 协议classic V2/V3 sensor、pixel
手段curl_cffi 单请求 + 协议 POSTV8 realm + 设备 / 行为 / 传输仿真
依赖仅 curl_cffi61MB sidecar + V8
验证样本24 行 + 107 壳268 站实测，3/27 validated
interstitial主方案Unsupported

结论：interstitial 语料继续走 gatekit；wre 只对“classic obfuscated sensor + curl 403 + 能产出 payload”的少数站有意义。

09Reproduce

复现命令

全部命令从仓库根目录执行；先按 wre/requirements.txt 装好并激活 venv，输出统一写到 wre/results/。

# 激活 venv（cmd: .venv\Scripts\activate.bat / PowerShell: .venv\Scripts\Activate.ps1）

python wre/scripts/probe.py  https://www.apahotel.com/ solve
python wre/scripts/verify.py https://www.ibm.com/

# 批量：读仓库内的 sites.csv
python wre/scripts/screen2.py 0 70
python wre/scripts/solve_batch2.py 0 6

# 稳定性复跑，重建总表与可视化数据
python wre/scripts/repeat2.py
python wre/scripts/make_report_data.py
python wre/scripts/build_visual_data.py

结果随出口 IP、时间与站点配置变化；这份快照只代表 2026-11-25 的观察，不代表长期可用性。

11Compliance

边界与合规

  • 样本来自 akamai.com 官网公开的 customer story 索引（sites.csv，268 主机，快照 2026-09-17），只访问公开首页。
  • 串行、每站一次 GET，并发 ≤ 2；未登录、未触达付费内容或个人数据。
  • 匿名首页会话 cookie 只在内存使用，未落盘。
  • 不 vendor 二进制；venv 与 61MB wred.exe 不随仓库发布，台账只作为本专题证据，不用于声明 gatekit 的支持范围。
  • 本专题不改变 gatekit 对 classic sensor / interstitial 的边界。
  • 工具输出（_abck 等）只作为测试记录，不用于生产采集。
